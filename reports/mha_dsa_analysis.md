## 结论

有帮助，尤其是依赖拆分、按生命周期配置buffer，以及首块PV直接初始化输出。
不能把DSA的约2倍加速当作当前MHA的预期结果，也不能照搬整套buffer版本数或缓存策略。
建议先确认本轮K/V双版本的设备收益，然后独立尝试首块PV直写O，或拆开S/alpha版本数定位问题。

## 两个算子的差异

| 属性 | 文档DSA固定源码 | 当前MHA比较 |
|---|---|---|
| query head数 | 64 | 1 |
| head_dim | 512 | 128 |
| KV | 共享的一份KV，稀疏索引gather | 独立K、V，连续访问 |
| 访问范围 | 每query选TopK，报告主要为TopK128 | 每query访问全部4096个key |
| KV块数 | TopK128时1块 | 32块 |
| 掩码 | caller提供因果有效前缀 | causal=False |
| 输出 | 固定提交实际为FP16 | 用户统一后的BF16 |
| 任务 | 多个query任务可由同核连续处理 | 32个Q tile，各逻辑block处理1个tile |

PR概要仍写FP32，但固定源码、输出Buffer、finalize和验证明确是FP16；本文以固定源码为准。
文档的性能表只作为那个DSA规格的报告数据，未在本机独立复现，不能外推到当前MHA。

## 第一份文档：算法与流水

### 可以优先借鉴：首块PV直接写O

DSA源码在block_id==0时将PV结果直接dual_copy到O_ub，后续块才执行
O=alpha*O+PV。因此没有预先清零O，也没有首块的乘零及加法累积。

我们的kernel仍在KV循环前clear_O_ub，所有32块都走accumulate_output。
首块在正常有限输入下，初始m=-inf、l=0，alpha=0，在线算法可把首块输出直接设为PV。
这是一项实际尚未做过、可保持稠密无掩码语义的改法。它只影响首块，预期空间有限；
首块/后续块条件分支及O/O_tmp生命周期可能影响自动调度，必须独立编译、检查精度并测量。
不能直接删掉清零而仍执行原来的首块累积，否则会读取未初始化O。

### 可以借鉴：把初始化放到消费者附近

DSA将m/l初始化放在首块softmax之前。我们现在把init_m_l放在KV流水线前。
可以尝试把它作为首块softmax的一部分，缩短生命周期、调整依赖边，但不保证减少时间：
当前每个逻辑block只有一个Q tile，与DSA跨多个query流水的场景不同。
建议先做首块PV改动，再单独测试初始化移动，不在一轮同时改变两处。

### 有直接启发：按生命周期配置buffer，而不是统一双缓冲

DSA的共享KV从gather一直活到PV，所以给3版本；S等用2版本；m/l等循环状态保留1版本。
当前MHA的K、V分别搬入，在不同阶段消费，生命周期与共享KV不同。
本轮数据正说明要按实际依赖判断：

- K/V从3改2：API降低1.20%，候选有收益。
- S/alpha从3改2：API约64.74us，明显退化。
- 全部改2：约64.14us，仍明显退化。

文档S=2有效，并不能证明我们的S=2有效。我们同时修改了S和alpha，
下一步若定位退化，需要分别测S=2/alpha=3和S=3/alpha=2，不能直接归因为S。
单版本是否妨碍重叠取决于读写时序；文档“任何一级单版本整条链都无法重叠”应按具体链路理解，
不能推广成所有buffer都必须多版本。

### 当前已经具备的技巧

- softmax使用vld2的偶/奇拆分、BF16 part转换、vor合并。
- 通过vsstb直接写NZ概率，随后P_nz_ub到P_shared，不另设概率ND暂存。
- P_nz_ub为ROWS+1，即65行的padding，已有对应pitch处理。
- Q从GM进入L1已在每个Q tile开始时只执行一次。
- 最终输出已改为BF16，并已融合归一化和转换。

文档的Q常驻指L1复用；我们刚测试的Q常驻指L0A复用，两者不是同一项优化。
前者已经存在，后者未观察到稳定API收益。

### 对当前规格帮助有限或不适用

- 两条稀疏行合成一条DMA：我们的K/V是连续tile搬运，没有逐index gather，不应改成稀疏路径。
- 因果块裁剪：当前causal=False，全部32个KV块都有效，不能跳过一半而保持语义。
- query/KV循环合并：当前NUM_M_TILES=32、NUM_BLOCKS=32，每block只有1个Q tile，
  没有同block相邻Q tile边界可重叠。若改成persistent任务分配才有研究价值。
- 直接启动28个block：当前源码要求32个M tile可被block数整除，28不满足。
  不均匀分配虽然可以另写，但仍有核做两个tile，不能假定尾部成本自动消失。
- 文档“128必须固定”是该SIMD实现的限制，不是硬件禁止其他KV分块；我们若改KV大小需重写打包。

## 第二份文档：搬运与模板

### 缓存策略可以测，但需要重新建立依据

文档提供了Q/O bypass L2的实验思路。对我们应分别测试Q输入和O输出策略，K/V先保留缓存：
每个K/V会被多个Q tile复用，一起bypass可能损失共享复用。
当前计时反复使用同一组输入，是稳定预热条件，不等同于每次调用都输入新地址的冷缓存场景。

“Q大于cache line，所以没有空间局部性”这个推理不成立：连续读取跨多条cache line，
并不消除空间局部性。是否bypass更应结合后续复用、缓存容量/污染、并发流量和实测。
当前Q/K/V/O各约1MiB，不能直接套用DSA长序列的大输出挤占L2结论。
文件中image-1.png到image-5.png未随仓库上传，无法核对图片中的实测数值与timeline。

### Roofline方法值得采用，文档数值不能照搬

当前两次GEMM名义工作量：4*4096*4096*128 = 8.59 GFLOPs，未计softmax等操作。
Q/O的最低逻辑流量共2MiB；Q/K/V/O各读写一次的最低量共4MiB。
但32个Q tile分别读取K/V，若不考虑缓存，逻辑K/V总读取可达64MiB，
加Q/O约66MiB。实际HBM读取量受L2命中与跨核复用影响，不能把这些逻辑量直接当HBM流量。
应测实际HBM/L2字节数及命中情况，再判断memory bound；不能只用Q/O下界推出已经带宽受限。
文档的1.47TB/s和378TFLOPS为文档当时采用的口径，不作为本机测量或设备参数确认值。

### 模板展开原则重要，但当前MHA已显式拆开主要步骤

DSA源码的GEMM输入在L1，并且PR声明依赖GEMM模板展开相关编译器工作。
我们的QK/PV已经显式写T.copy(L1,L0A/L0B)、T.gemm(L0A,L0B,L0C)及dual_copy，
生成C++也可见独立l12l0和mad。不能假定重新套用L1 GEMM模板就会得到相同收益。
同样，softmax已经直接产生NZ概率，不存在文档稀疏KV的“gather后隐藏ND2NZ”整条链。
可继续检查具体同步和lowering，但不建议只为这份DSA示例直接升级服务器编译器；
如测试依赖PR，需固定版本并重新验证原始基线与候选，避免将编译器变化算成kernel改动收益。

## 建议顺序

1. 对本轮K/V双版本采集设备Duration，确认API的约1.2%额外收益。
2. 在确认后的最佳组合上，独立测试首块PV直接初始化O，避免清零与首块累积。
3. 如需定位buffer退化，拆开S和alpha版本数；不把明显较慢组合加入下一轮默认最佳。
4. 单独测Q/O的L2策略，并区分当前预热重复输入与实际业务输入复用条件。
5. persistent任务分配、跨Q tile循环合并以及编译器pass改动作为较大后续实验。

后续设备复核已确认K/V双版本组合为当前最佳：约51.071us，较同轮原始TL降低3.00%。
详见reports/mha_buffers/report.md。首块PV直接初始化O的候选已准备，NPU验证待执行。
